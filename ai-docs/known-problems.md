# Known problems

Mistakes that break EasyDeploy projects again and again. Find the row whose
symptom matches what you see, then apply its fix in the repository and deploy
again. Read the project detail, workflow steps, and logs first (see "When a
deploy fails" in `AGENTS.md`) so you match the real symptom, not a guess.

| Symptom | Cause | Fix |
| --- | --- | --- |
| The rollout never becomes ready, or the service URL answers Bad Gateway. | The app listens on a different port than the service's `port` in `easydeploy.yaml`, or only on `127.0.0.1`. | Listen on `0.0.0.0` at the `PORT` value. Keep `port` in `easydeploy.yaml` and `PORT` in `.env` equal. If the runtime does not read `.env`, set `ENV PORT=<port>` in the Dockerfile. |
| The image build fails because `COPY` cannot find a file. | The build context is the Dockerfile's folder. A Dockerfile in a subfolder cannot copy files from the repository root. | Keep the Dockerfile at the root with `dockerfile: Dockerfile`, or copy only files inside the Dockerfile's folder. |
| A password, key, or token is in Git history and inside the image. | It was committed in the tracked `.env`, which the image copies. | Remove it from `.env`, rotate it, and set it on the project's Variables page for dev and prod. The tracked `.env` holds public defaults only. |
| Redirects go to `http://` or an internal host; OAuth or SSO callbacks fail with a redirect mismatch. | The app runs behind an HTTPS gateway and ignores `X-Forwarded-Proto` and `X-Forwarded-Host`. | Turn on the framework's trusted-proxy setting (for example Express `trust proxy`, Django `SECURE_PROXY_SSL_HEADER`, Spring `server.forward-headers-strategy`). Register the callback with the service's deployed `url`. |
| The container restarts in a loop (`CrashLoopBackOff`) right after it starts. | A required variable exists only in a local, untracked `.env`, so the deployed app starts without it. | Read the startup error in the logs. Add public defaults to the tracked `.env`; set private values on the Variables page for dev and prod. |
| After renaming a service, its link changed, or the old link still opens an old version. | The service name is part of the service's host and object names. A rename creates new ones and leaves the old ones running. | Avoid renaming deployed services. If you rename one, take the new address from the project detail's `url` and ask the platform team to remove the old service. |
| The deploy fails at the `descriptor` step. | `name` in `easydeploy.yaml` is not the project's name, for example after copying the file from another repository. | Set `name` to the project name (`PROJECT_NAME` in `.env`). Never copy `easydeploy.yaml` from another project. |
| Pods stay in `ImagePullBackOff`. | `image` points to an image or tag that does not exist or that the cluster cannot pull. | Fix the reference, or build the service from a Dockerfile instead of `image`. |
| After changing `port` or toggling `public`, the URL answers Bad Gateway or times out. | The change was applied only partly: the app, `.env`, and `easydeploy.yaml` disagree, or the old route is still in place. | Change the app, `PORT` in `.env`, and `port` in `easydeploy.yaml` in one commit. After the deploy, check `health` and `url` in the project detail. If the old route stays, contact the platform team. |
| Builds are slow, images are large, and the repository fills up with copied files. | Shared code sits outside each service's build context, so every service builds from the root and copies the whole tree. | Give each service a Dockerfile that copies only what it needs, add a `.dockerignore`, and do not commit generated or copied output. |
| Hosts do not match the live ones, or routing changes revert or conflict. | The repository has its own Ingress manifests, or a CI job that applies them to the cluster beside the platform. | Delete them. The platform owns routing: set `public: true` on the service and read its address from `url`. |
| One push deploys twice, or deploys overwrite each other. | In-repository build and deploy workflows (for example GitHub Actions or `repository_dispatch`) form a second deploy path. | Remove them. Pushing `main` deploys dev and pushing a `v` tag deploys prod. CI that only runs tests is fine. |
| The build works on a Mac but fails in the image, for example a missing native module in a Vite build. | Dependencies were resolved on macOS, or the host's installed dependencies were copied into the image, so Linux native packages are missing. | Exclude `node_modules` and build output in `.dockerignore`, install dependencies inside the image (`npm ci` or the equivalent), and regenerate the lockfile if Linux packages are missing from it. |
| Data disappears after every redeploy or restart, and migrations run from scratch. | A database runs as a plain service with no volume. Persistent storage (`persistence`) is not available yet. | Do not keep data inside service containers. Use a managed database and pass its connection string as a private Variable. |
| Some files always show as modified on macOS or Windows. | The repository has files whose names differ only by letter case. | Rename or delete one of each pair so every path is unique ignoring case. |
